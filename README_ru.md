# HashHush

Эфемерный групповой чат со сквозным шифрованием, поставляемый **одним самодостаточным бинарником на C++ со встроенным внутрь фронтендом** — без отдельного веб-каталога, внешнего сервера статики и каких-либо runtime-зависимостей помимо системных библиотек. Комнаты существуют ровно столько, сколько ими пользуются; сервер не способен прочитать содержимое сообщений, никогда не получает ключ шифрования и не сохраняет полную историю переписки.

Проект — иной взгляд на ту же идею, что лежит в основе [niltalk](https://github.com/knadh/niltalk): чаты без регистрации, доступные по ссылке. HashHush заменяет cookie-сессионную модель niltalk на полностью клиентское сквозное шифрование, передачу ключа через якорь URL и стабильный внутрикомнатный идентификатор, выводимый из access-токена, — так что приватность сохраняется даже при полном компрометации сервера.

## Возможности

- **Сквозное шифрование** XChaCha20-Poly1305 (libsodium, в WebAssembly). Сервер видит только зашифрованные блоки.
- **Ключ шифрования никогда не передаётся на сервер.** Восьмисимвольный seed-ключа находится в якоре URL (`#`), который браузеры не отправляют. На загрузке страницы сервер видит только путь `/`.
- **Опциональный пароль.** Дополнительный секрет, который участники согласуют отдельным каналом. С паролем одной только ссылки недостаточно — полезно, когда ссылка идёт менее доверенным каналом, чем пароль.
- **Защита от перебора комнат.** «Комнаты не существует», «неверный ключ» и «неверный пароль» дают одинаковый ответ на уровне WebSocket — атакующий не может перебирать случайные id, чтобы выяснить, какие из них реальны.
- **Эфемерные комнаты.** Комната автоматически удаляется по бездействию (по умолчанию 24 часа с момента последнего сообщения) или вручную любым из участников.
- **Без регистрации.** Никнейм — необязательная подпись. Внутри комнаты у участника стабильный идентификатор, выводимый из access-токена; он переживает перезагрузки страницы и не требует хранить ничего чувствительного.
- **Пул одноразовых челленджей** для первичных подключений. Создатель комнаты загружает `(5 или 10) * max_participants` троек `(plaintext, ciphertext, nonce)`, зашифрованных под ключом комнаты — `×10` если задан пароль, `×5` иначе. Новый участник получает доступ только после расшифровки одной из них; повторно тройка не используется.
- **Перманентные access-токены и кеш ключа.** После успешного первичного входа сервер выдаёт токен; клиент сохраняет в `localStorage` токен и проверенный ключ. Пароль удаляется из памяти JS сразу после вычисления ключа, поэтому повторный ввод при перезагрузке не требуется.
- **QR-код для шеринга.** Модальное окно отрисовывает QR ссылки локально, без внешних запросов.
- **Развёртывание одним бинарником.** Фронтенд на Svelte 5 собирается в один HTML-файл и встраивается прямо в исполняемый файл C++.
- **Не требует HTTPS.** Вся криптография выполняется локально в браузере через libsodium; приложение корректно работает по обычному `http://`.

## Принцип работы

### Схема URL

```
https://host/#<roomId>:<seed>
```

Путь всегда `/`. И идентификатор комнаты, и seed-ключа находятся в якоре URL. Якорь обрабатывается исключительно браузером — сервер при загрузке страницы его не получает. Последующие API-запросы передают идентификатор комнаты, но не seed.

### Создание комнаты

1. `POST /api/rooms { name, requires_password }` создаёт неактивную комнату и возвращает `{ room_id, max_participants, challenges_required }`. `challenges_required` равно `5 * max_participants` для комнаты только-по-ссылке и `10 * max_participants` при заданном пароле.
2. Клиент генерирует случайный восьмисимвольный seed, вычисляет симметричный ключ из `(seed, password)` (см. *Вычисление ключа*) и формирует `challenges_required` троек `{ plaintext, ciphertext, nonce }`, где `ciphertext = AEAD_encrypt(key, nonce, plaintext)`, а `plaintext` — 32 случайных байта.
3. `POST /api/rooms/{id}/activate { challenges }` загружает тройки. Сервер сохраняет только base64-блобы — расшифровать их он не в состоянии и ни seed, ни пароль не получает.
4. Комната становится активной. Адресная строка переписывается на `/#<roomId>:<seed>`. Пароль (если задан) сохраняется только как готовый ключ в `localStorage`; в открытом виде нигде не передаётся и стирается из памяти JS сразу после вычисления ключа.

### Подключение

Открывается WebSocket на `/ws?room=<id>` (опционально `&token=<t>` для возвращающегося участника). Upgrade проходит для любого непустого `room` — даже если такой комнаты нет — чтобы перебор случайных id не позволял выяснить, какие комнаты реальны.

- **Возвращающийся участник с сохранённым токеном** отправляет `{ type: "hello", token }`. Сервер проверяет токен и отвечает `{ type: "joined", peer_id, room_name, members, history }`. Любая ошибка (несовпадение токена, удалённая комната) закрывает соединение общим кодом `invalid_key`.
- **Первичное подключение** отправляет `{ type: "hello" }`. Сервер отвечает `{ type: "challenge", ciphertext, nonce }` — реальной тройкой, если комната есть и пул не пуст, либо случайной декорацией в противном случае. Клиент расшифровывает и отвечает `{ type: "challenge_response", plaintext }`. При совпадении сервер выпускает новый access-токен и завершает вход; при любом расхождении соединение закрывается с `invalid_key`.
- **Неверный пароль** даёт ту же реакцию сервера, что и «неверный ключ»; клиент различает их локально и предлагает пользователю ввести пароль повторно.

`peer_id` — это первые 16 шестнадцатеричных символов `SHA-256(token)` — детерминирован от токена, поэтому одна и та же вкладка получает один и тот же идентификатор после перезагрузок. Закешированные сообщения хранят идентификатор отправителя, что позволяет вернувшемуся клиенту распознать собственные старые сообщения без участия сервера.

Если пул челленджей исчерпан (жёсткий лимит — `5 *` или `10 * max_participants` успешных входов через challenge за время жизни комнаты), сервер уходит на путь декорации, и пользователь видит результат, эквивалентный «неверному паролю».

### Поток сообщений

- Чат: `{ type: "msg", payload }`, где `payload = base64(nonce || ciphertext)` из JSON-объекта `{ kind: "chat", text, nick }`.
- Presence (анонс никнейма): `{ type: "presence", payload }` для `{ kind: "presence", nick }`.
- Сервер **кеширует** только фреймы `msg` в кольцевой буфер на комнату (по умолчанию 5 записей). Presence-фреймы лишь ретранслируются, но не сохраняются, поэтому не могут вытеснить реальные сообщения из буфера.
- Сервер транслирует фрейм всем подключённым участникам. Новый участник получает содержимое кеша один раз, в составе фрейма `joined`.

### Вычисление ключа

Четыре раунда SHA-256 с литеральными солями, конкатенирующимися с результатом предыдущего раунда как сырые байты. В четвёртом раунде солью выступает опциональный пароль (пустая строка при отсутствии пароля — цепочка имеет одну фиксированную форму):

```
k₀ = SHA-256("hash"       ‖ seed_utf8)
k₁ = SHA-256("hush"       ‖ k₀)
k₂ = SHA-256("chat"       ‖ k₁)
k₃ = SHA-256(password_utf8 ‖ k₂)   // 32 байта — ключ XChaCha20-Poly1305
```

Неверный пароль даёт неверный ключ; ответ на challenge не совпадёт, сервер закроет соединение с `invalid_key`, клиент покажет форму ввода пароля.

### Что хранит сервер

| Хранилище   | Содержимое                                                          | Назначение                                                                            |
|-------------|---------------------------------------------------------------------|---------------------------------------------------------------------------------------|
| SQLite (диск) | `rooms`, `challenges`, `access_tokens`                              | Переживает рестарт. Ничего из этого не позволяет серверу расшифровать сообщения.       |
| ОЗУ          | Активные WebSocket-подключения и кольцевой буфер из N сообщений      | Теряется при рестарте; клиенты переподключаются по сохранённому токену.               |

Сервер не хранит транскрипта, не видит открытого текста, не получает seed и производный ключ. Полный дамп SQLite-файла даст атакующему ciphertext-челленджи и access-токены — этого достаточно лишь для того, чтобы выдать себя за участника на уровне WebSocket (но и тогда сообщения остаются нечитаемыми без ключа).

## Сборка

### Только серверная часть

Требуется компилятор C++20, CMake 3.16 или новее и системная библиотека SQLite (`libsqlite3-dev` в Debian/Ubuntu). Перед сборкой серверной части необходимо собрать клиентскую (см. ниже).

```sh
cmake -B build
cmake --build build
```

### Полная сборка (клиентская и серверная части)

Дополнительно требуются Node.js версии 18 или новее и npm.

```sh
# 1. Сборка клиентской части.
cd web
npm install
npm run build       # формирует web/dist/index.html (одностраничное приложение)
./embed.sh          # генерирует src/generated_index_html.h
cd ..

# 2. Сборка серверной части со встроенным веб-интерфейсом.
cmake -B build
cmake --build build
```

Полученный исполняемый файл отдаёт SPA по адресу `/`, REST-эндпоинты по `/api/` и WebSocket по `/ws`. Отдельный сервер статических файлов не требуется.

### Версионирование

Строка версии формируется на этапе CMake-конфигурации командой `git describe --tags --dirty`; ведущий `v` отбрасывается. При отсутствии тегов используется значение `dev`. Та же строка подставляется в `src/version.h` для бинарника и в `web/src/version.js` для бандла фронтенда — поэтому подвал страницы и стартовая запись лога всегда показывают одно и то же.

## Запуск

```sh
# Показать справку.
./build/src/hashhush --help

# Сгенерировать конфигурацию по умолчанию.
./build/src/hashhush --generate-config ./config.ini

# Запустить сервер.
./build/src/hashhush --config ./config.ini
```

### Конфигурация

Полный перечень параметров приведён в файле [`contrib/config.ini.example`](contrib/config.ini.example). Ключевые опции:

- **`[server] app_name`** — название, отображаемое в заголовке главной страницы. Текст ссылки в подвале зафиксирован как `HashHush` и не зависит от конфигурации.
- **`[storage] db_path`** — путь к SQLite-файлу.
- **`[room] default_max_participants`** — вместимость комнаты (по умолчанию 10). Размер пула челленджей — `5 * max_participants`.
- **`[room] idle_ttl_seconds`** — время бездействия до удаления комнаты (по умолчанию 86400).
- **`[room] message_cache_size`** — размер кольцевого буфера сообщений (по умолчанию 5).
- **`[room] ws_max_payload_bytes`** — максимальный размер полезной нагрузки WebSocket после base64-кодирования.

## Модель угроз

HashHush защищает **конфиденциальность и целостность сообщений** от:

- Пассивного наблюдателя HTTP/WebSocket-трафика без TLS.
- Полностью скомпрометированного оператора сервера с доступом к диску и оперативной памяти.
- Участников других, не связанных, комнат на том же инстансе.

HashHush **не** защищает от:

- Атакующего, владеющего якорной частью URL (`#<roomId>:<seed>`) **и** паролем (если он задан). Обладатель обоих факторов — участник по определению.
- Зловредного участника той же комнаты — он по построению владеет ключом.
- Активного MITM на канале без TLS, перехватывающего WebSocket-фреймы в реальном времени. Опередив легитимного пользователя при пересылке его `challenge_response.plaintext`, он выигрывает гонку за конкретный challenge и получает валидный access-токен. Ключа у него по-прежнему нет — ни live-, ни кешированные сообщения он расшифровать не может. Но он занимает слот в комнате, виден в списке участников, может слать в канал «мусорные» байты (другие клиенты их молча отбрасывают на этапе AEAD-проверки) и, поскольку токен валиден, **может удалить комнату через `DELETE /api/rooms/{id}`**. Установка TLS перед HashHush полностью снимает этот класс угроз.

## Признательность

Идею одноразовых, безаккаунтных, доступных по ссылке чатов задал [niltalk](https://github.com/knadh/niltalk). HashHush берёт эту идею и переосмысляет её в строгом сквозном шифровании, доставке ключа через якорь URL и минимальной осведомлённости сервера — чтобы приватность сохранялась даже тогда, когда сервер её не защищает.
